# Account and private portal review — local PR only

Customer registration remains open, as explicitly requested by the owner. An account is not required to request a quote. Ordinary accounts receive no operator role from their email domain or alias. Staff status requires verified email and one of the two exact configured owner addresses, or a verified identity with the boolean `admin` custom claim. The browser also checks the verified-email claim from the ID token. These checks do not grant any remote role.

The public App no longer imports the Firebase runtime. Authentication loads when an account route or explicit authentication action needs it. Session lifecycle tests cover StrictMode cleanup during an SDK load, a stale claim result, account replacement, an in-flight login followed by logout, unmounts and retry after a failed SDK load. SDK mutations are serialized so a late login cannot complete after sign-out and silently restore a session. Account forms start empty, have six-language copy, and send authentication details only through Firebase. The previous fallback account creation after failed login and example credentials are removed.

If an old example credential was an actual password, the owner should rotate it and review sessions separately. No credential value is reproduced here. No sign-in, account creation, password reset, role grant, production data change or email delivery was performed during this review.

The private portal clears views on account/role changes and discards late query/write results belonging to a previous identity. It creates no sample jobs on mount. Manual requests require an explicit amount and service; invented price/contact fallbacks were removed. This does not change the booking calculator or payment engine. The old browser email automation hook is removed. Staff can preview and explicitly open a mailto draft; that action does not report a message as sent. Preview HTML uses an opaque sandbox and restrictive document CSP. Client mail history and confirmation flags are no longer retained in localStorage.

`firestore.rules` is revised locally and **has not been applied remotely**. The proposed rules require verified staff identities, preserve record owners, restrict client updates to allowed fields on pending/draft requests and prevent clients from changing operational status, price/payment data or application decisions. Server-side booking storage uses its existing authenticated capabilities and Admin SDK flow. The calculator/outbox/payment gates are unchanged.

Before any later rule deployment, the owner must verify that the intended staff accounts can authenticate and satisfy the verified-email/custom-claim requirements. Review these rules against existing production document shapes and run an emulator/staging rules test before applying them. The local integration test was skipped because Java Runtime is missing, so this review does not claim an emulator or production authorization test. The retained anonymous intake and historical local notes require the separate decisions recorded in [PRIVACY_FIRESTORE_AUDIT.md](./PRIVACY_FIRESTORE_AUDIT.md). The field allowlist/diff pattern follows [Firebase's field access guidance](https://firebase.google.com/docs/firestore/security/rules-fields); [custom claims](https://firebase.google.com/docs/auth/admin/custom-claims) remain a trusted server administration operation.

Validation includes TypeScript, ten focused account/session/security tests, local HTTP header/CORS tests and booking/recovery regression tests. No external message, role or account action is part of those tests.
